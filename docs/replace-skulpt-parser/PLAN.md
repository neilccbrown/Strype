# Replacing Skulpt with web-tree-sitter in `pythonToFrames.ts`

Status: **planning only, nothing implemented yet**. Written at high reasoning
effort so it can be hastily re-read at low effort and executed step by step.
Branch: `replace-skulpt-parser` (created from upstream `main` @ `cf09ac07`).

## 0. Scope

In scope: `src/helpers/pythonToFrames.ts` — specifically its use of
`Sk.parse()` / `Sk.ParseTables.sym.*` / `Sk.builtin.SyntaxError` to turn pasted
or loaded Python/SPY source text into a concrete syntax tree that
`copyFramesFromPython()` walks to build Strype `FrameObject`s. There is no
`framesToPython` (the reverse direction, frames → Python text) work here —
that direction doesn't use Skulpt at all today and is untouched.

**Skulpt itself turns out to be fully removable as part of this work, not
just this one consumer of it.** Checked directly: `declare const Sk` and
every live call to the `Sk.` global in `src/` exist *only* in
`pythonToFrames.ts`.
- Execution already runs entirely through **Pyodide**
  (`src/stryperuntime/*`, `pyodide-0.29.0` assets cached by the service
  worker) — `PythonExecutionArea.vue`/`execPythonCode.ts` have zero Skulpt
  references.
- Autocomplete's `src/autocompletion/python-api.json` is generated by
  `scripts/process-pyodide-api.ts` (wired into `package.json`'s
  `preprocess:update-python-api`), not `scripts/compiled/scripts/process-skulpt-api.ts`
  (which exists in the repo but is dead — not referenced by any
  `package.json` script). `acManager.ts`'s `allSkulptItems` naming is just a
  leftover variable name from when this data came from Skulpt; it doesn't
  call Skulpt at runtime.

So Skulpt is already vestigial outside of parsing — it's shipped today
(`public/js/skulpt.min.js` 605KB + `skulpt-stdlib.js` 480KB = **1085KB**,
loaded eagerly via blocking `<script defer>` tags in `index.html` on every
app start, regardless of whether the user ever pastes/loads Python) purely
to support this one file. **Once the parser is swapped, remove Skulpt
entirely**: delete the two `<script>` tags in `index.html`, delete
`public/js/skulpt.min.js` and `public/js/skulpt-stdlib.js`, and delete the
dead `scripts/compiled/scripts/process-skulpt-api.ts` (confirm nothing else
references it first). This also corrects the bundle-size accounting in §1 —
see the note there.

`public/js/skulpt.min.js` was a **vendored, customized fork** with no source
in this repo — its comments in `pythonToFrames.ts` reference grammar
permissiveness added specifically for Strype (e.g. gluing `elif`/`except` on
to standalone joint-frame pastes, and a hand-relaxed `match`/`case` grammar
that only became necessary because upstream Skulpt didn't support PEP 634).
Beyond the parser-quality improvements in §1, this migration also removes a
dependency on that opaque, unmaintained, un-buildable-from-source binary
entirely, in favour of the actively maintained upstream `tree-sitter-python`
grammar.

## 1. Suitability of web-tree-sitter — findings

**Verdict: suitable, and structurally a better fit than Skulpt's CST, but
this is a substantial rewrite of `copyFramesFromPython`/`toSlots`, not a
drop-in swap.** Key findings:

- **Packaging**: `web-tree-sitter` (npm) is the WASM binding; it needs
  `await Parser.init()` once, then `Language.load('/path/to/tree-sitter-python.wasm')`.
  Both the core runtime (`tree-sitter.wasm`, ~250KB) and the Python grammar
  (`tree-sitter-python.wasm`, ~450KB) are plain static files — exactly the
  same shape as the current `public/js/skulpt*.js` vendoring, so the natural
  approach is to drop both `.wasm` files into `public/js/` and `fetch()`
  them at runtime, not to make Vite bundle them.
  **Bundle-size accounting, corrected**: since §0 established Skulpt is
  fully removable (not just this one consumer of it), this is **not** a
  700KB addition on top of Skulpt — it's ~700KB replacing 1085KB
  (`skulpt.min.js` + `skulpt-stdlib.js`), a net reduction, and that 1085KB
  is currently loaded *eagerly* on every app start via blocking
  `<script defer>` tags regardless of whether Python is ever pasted/loaded.
  Lazy-load the two `.wasm` files only when a paste/load actually happens
  (`Parser.init()` + `Language.load()` on first use, cached thereafter) so
  the 700KB doesn't even hit the initial-load critical path — i.e. this
  change should be a strict improvement to both initial load size *and*
  total shipped size, not a tradeoff.
- **Runs in Node.js too** (slower than native, but fine for test purposes) —
  this is a real enabler: it means `copyFramesFromPython`/`toSlots`-equivalent
  logic could get **Vitest unit tests** for the first time. There is
  currently no unit test runner in this repo at all (`tests/unit` mentioned
  in `CLAUDE.md` does not currently exist — confirmed via `git log --all`,
  it's aspirational/from a different line of work, not present on this
  branch). Today the *only* regression coverage for this file is full
  browser e2e (Cypress/Playwright) driving paste/load through the UI. This
  migration is a good opportunity to add a fast, browser-free unit-test
  layer directly against the new parsing module, in addition to keeping the
  e2e safety net.
- **Grammar shape is a major improvement over Skulpt's CST**:
  `tree-sitter-python`'s `grammar.js` uses named `field()`s extensively —
  `if_statement` has `condition`/`consequence`/`alternative`, `for_statement`
  has `left`/`right`/`body`/`alternative`, `function_definition` has
  `name`/`parameters`/`return_type`/`body`, `class_definition` has
  `name`/`superclasses`/`body`, `match_statement` has `subject`/`body`,
  `except_clause` has `value`/`alias`, `assignment`/`augmented_assignment`
  have `left`/`right`/`operator`, `subscript` has `value`/`subscript`,
  `for_in_clause` has `left`/`right`, `default_parameter` has `name`/`value`,
  etc. This replaces the current code's fragile-to-grammar-change
  "third child is the condition, fourth is body" positional indexing
  (`makeAndAddFrameWithBody(p, ..., 0, [1], 3, ...)` style) with
  `node.childForFieldName('condition')`-style lookups, which is both more
  readable and more robust.
- **Comments and whitespace are handled natively**, unlike Skulpt: `$.comment`
  is declared in `extras` (`extras: $ => [$.comment, /[\s\f...]|\r?\n/, $.line_continuation]`),
  meaning comment nodes **appear in the tree** at their real source position
  (row/column), rather than being stripped before parsing the way Skulpt
  requires. Blank lines are not emitted as nodes (whitespace-only extras
  aren't materialized), but every node carries exact `startPosition`/
  `endPosition` (row, column) and the source text is sliceable by byte
  offset — so blank-line detection becomes "gap in row numbers between two
  sibling nodes / into a block's start", computed directly from positions,
  rather than needing Skulpt's pre-parse disguise-as-fake-statement trick.
  See §2 for how this changes the comments/blanks design.
- **Error recovery, not exceptions**: `Sk.parse()` throws on invalid syntax
  (which the current code catches and turns into `CopyFailure`). Tree-sitter
  instead *always* returns a tree, inserting `ERROR`/`MISSING` nodes for
  unparseable input (`tree.rootNode.hasError()` to check). This is workable
  but changes the error-reporting code path — see §5 "error messages" below,
  it's a real behavioural difference that needs a decision, not just a
  mechanical port.
- **Match/case**: full PEP 634 support (`match_statement`, `case_clause`,
  literal/OR/guard/class/sequence/mapping patterns) is built into upstream
  `tree-sitter-python` — i.e. we no longer need Strype's own relaxed-grammar
  Skulpt fork for this. Also: `checkValidMatchContent()`
  (`pythonToFrames.ts:1907`) exists purely to reject non-`case` children
  directly under a `match` block, because the customised Skulpt grammar is
  *permissive* there (allows bare simple statements as direct children of
  `match`, which real Python forbids). Standard `tree-sitter-python`'s
  `match_statement.body` is aliased to `$._match_block`, which structurally
  only accepts `case_clause`s — so this workaround likely becomes
  unnecessary and can be deleted (confirm during implementation by trying to
  parse invalid direct-match-content and checking it comes back as an
  `ERROR`/rejected node rather than silently succeeding).
- **Other constructs confirmed present** in `tree-sitter-python`: walrus
  (`named_expression`), f-strings (`string`/`interpolation`/
  `format_specifier` — NB: Strype currently treats an entire f-string as one
  opaque string blob per `toSlots()`'s `strMatch` regex, so f-string internal
  structure must be *flattened back* to raw source text rather than walked;
  since tree-sitter nodes carry exact byte ranges this is actually easier
  than reconstructing token values the way `digValue()` does today — just
  slice the original source string for the `string` node's range),
  async `def`, positional-only (`/`) and keyword-only (`*`) parameter
  markers, the Python 3.10+ parenthesised multi-item `with (a, b):` form.
  None of these are currently pasteable/exercised by tests (see §4). The
  plan does not require newly supporting any of them — Strype's frame model
  may not have UI for them at all — but they should at least fail
  gracefully (clear "unsupported" error) rather than crash, and this should
  be a deliberate decision per construct, not an accident of what the
  switch statement happens to handle.
  **Decorators are a confirmed exception**: Strype doesn't support them, so
  this is settled, not a per-construct decision — pasting/loading a
  decorated `def`/`class` should produce a clear "unsupported" error, and
  the corresponding test (§4.2) should assert that error rather than test
  for the feature.
- **License**: tree-sitter core and `tree-sitter-python` are MIT — no
  conflict with vendoring alongside Skulpt.
- **Sourcing the `.wasm` files**: two options, needs a decision (§5):
  (a) build `tree-sitter-python.wasm` ourselves from the pinned
  `tree-sitter-python` npm package via `tree-sitter build --wasm` (requires
  Emscripten locally or in CI — one-time/occasional build step, output
  committed to `public/js/` like Skulpt is today), or (b) consume a
  third-party prebuilt bundle (e.g. the `tree-sitter-wasms` npm package)
  that ships a ready-made `tree-sitter-python.wasm`, trading a small
  supply-chain/trust/staleness risk for zero build tooling. Recommend (a)
  for provenance (matches how the project already treats vendored
  parser/runtime binaries) unless Emscripten-in-CI proves painful.

## 2. Comments & blanks: recommended design change

**Recommendation: do NOT keep the current disguise/undisguise pass as-is.**
The existing `transformCommentsAndBlanks()` (~280 lines) exists almost
entirely to work around two Skulpt limitations that tree-sitter doesn't
have:

1. Skulpt drops comments and blank lines entirely, so they're rewritten as
   fake identifier statements (`___strype_comment_<escaped>`,
   `<indent>___strype_whole_line_blank`) before parsing, then decoded back
   out of the resulting tree afterwards.
2. Skulpt's indentation-sensitive parse fails if a comment's own indentation
   doesn't match its surrounding code (Python itself allows arbitrary
   comment indentation) — hence `checkRearrangeCommentsIdent()` rewriting
   comment-block indentation before parsing.

With tree-sitter, comments are real nodes at their real position and
indentation is a non-issue for comments (grammar-level `extras`, not
indentation-sensitive), so most of this goes away. Recommended new shape:

- A **much thinner preprocessing pass** over raw source lines that only
  handles genuinely Strype-specific, non-Python syntax that tree-sitter's
  Python grammar cannot know about:
  - `#(=> Disabled:` — this one is *not* a standalone comment, it's a prefix
    stripped from the front of a real code line (`codeLines[i] =
    directiveIndent + value` in the current code) — still needs a line-level
    strip-and-record pass before feeding source to tree-sitter, recording
    which resulting line number was disabled.
  - `#(=> Library:` / `#(=> LibraryDisabled:` / `#(=> FrameState:` — these
    *are* whole-line, comment-shaped directives. With tree-sitter they can
    be recognised directly from `comment` nodes' text in the tree (matched
    against the `AppSPYFullPrefix` regex) instead of needing the current
    encode-as-fake-statement dance — simpler, and removes another category
    of "decode after parse".
  - Triple-quoted multi-line strings: verify `tree-sitter-python`'s string
    rule (external scanner) handles these as a single multi-line `string`
    node natively (very likely, this is standard for any real Python
    grammar) — if so, the current line-collapsing/`STRYPE_DOC_NEWLINE`
    machinery in `transformCommentsAndBlanks()` for triple-quoted strings
    can be dropped, and the string's raw text can be read directly via
    source-slicing on the node's byte range.
- **Blank-line detection**: derive post-parse, by walking each block's
  children (statements + comment `extra` nodes, still ordered by position)
  and comparing `node.endPosition.row` of one to `node.startPosition.row` of
  the next (and the block's own start/end rows for leading/trailing blanks).
  A gap > 1 row = one or more blank lines. This replaces
  `STRYPE_WHOLE_LINE_BLANK` marker-line insertion and the elaborate
  indentation-inheritance logic (`smallestAdjIndent`,
  `nextIsJointContinuation`, etc.) in the current blank-line branch — the
  *placement* logic (which block a blank line's frame belongs to, i.e. is it
  before an `elif`/`else`/`except`/`finally` continuation) still needs
  equivalent reasoning, but computed from the tree's real structure (is the
  next sibling node inside the same block or does the row gap span a block
  boundary) rather than from re-scanned raw text indentation.
- **Comment placement**: since `comment` nodes appear in `extras` (not as
  children of the specific statement list you're iterating unless you use a
  cursor that includes extras, or a separate pass merging positions) —
  during implementation, confirm exactly how `web-tree-sitter`'s JS API
  surfaces extra nodes when walking children (e.g. does `node.children`
  include them, or do you need `node.namedChildren` vs a raw child walk, or
  a tree cursor with `gotoFirstChild()`/`gotoNextSibling()` that does
  include extras). This is a concrete unknown to resolve early (spike, see
  §3 step 1) since the whole comment/blank design in this section hinges on
  it.
- **What must be preserved as-is regardless of parser**: the joint-frame
  gluing trick in `parseWithSkulpt()` (prepend a fake `if True:\n    pass\n`
  or `try:\n    pass\nexcept:\n    pass\n` before parsing text starting with
  a bare `elif`/`else`/`except`/`finally`, then detach the fake parent after)
  — this is parser-agnostic and should port unchanged, just targeting
  tree-sitter's parse instead of Skulpt's. `STRYPE_INVALID_SLOT` /
  `STRYPE_INVALID_OPS_WRAPPER` / `STRYPE_INVALID_OP` (used by the *reverse*
  direction, frames → Python text, to round-trip content Python can't
  represent) are also unaffected — they're just identifiers/tokens from
  tree-sitter's point of view like any other, still decoded the same way
  after parsing.

## 3. Implementation plan

Suggested order, each step should leave `main`/the branch buildable and
(where noted) with tests green:

1. **Spike (no product code change)**: get `web-tree-sitter` + a
   `tree-sitter-python.wasm` parsing a handful of representative snippets
   (plain statement, `if/elif/else`, comment-before-def, blank-line-in-body,
   triple-quoted docstring, `match`/`case`, standalone `elif`) in an
   isolated script (Vitest test or throwaway node script), to nail down:
   the exact web-tree-sitter API surface (`Parser`, `Language.load`,
   `tree.rootNode`, `node.childForFieldName`, cursor API), how `extras`
   (comments) surface when walking, and how `ERROR`/`MISSING` nodes look for
   a few classes of invalid input. This resolves the open unknown in §2 and
   de-risks everything after it.
2. **Decide and implement `.wasm` sourcing** (§1, build-vs-vendor decision),
   add the files under `public/js/`, add lazy-load plumbing (fetch +
   `Parser.init()` + `Language.load()` on first use, cached thereafter —
   mirror how Skulpt's `Sk.configure({})` is called lazily per-parse today
   but make the wasm fetch itself one-time and async-await-able from
   `parseWithSkulpt`'s replacement).
3. **New thin preprocessing pass** replacing `transformCommentsAndBlanks()`
   per §2 — only SPY-directive stripping (`Disabled:`) survives in
   meaningfully similar shape; keep `disabledLines`/`frameStateLines`/
   `strypeDirectives` output shape the same so downstream code
   (`copyFramesFromParsedPython`, `addFrame`) doesn't need to change.
4. **New tree-walking core** replacing `copyFramesFromPython`/`toSlots`/
   `digValue`/`getRealLineNo`/etc., driven by tree-sitter's field API
   instead of positional child indices. This is the bulk of the work — go
   construct-by-construct against the existing `switch` cases as a
   checklist (`file_input`→`module`, `if_stmt`→`if_statement`,
   `while_stmt`→`while_statement`, `for_stmt`→`for_statement`,
   `try_stmt`→`try_statement`+`except_clause`, `with_stmt`→`with_statement`,
   `funcdef`→`function_definition`, `classdef`→`class_definition`,
   `match_stmt`/`case_block`→`match_statement`/`case_clause`,
   `expr_stmt`→`assignment`/`augmented_assignment`/`expression_statement`,
   `import_name`/`import_from`→`import_statement`/`import_from_statement`,
   `global_stmt`→`global_statement`, `raise_stmt`/`return_stmt`/
   `pass_stmt`/`break_stmt`/`continue_stmt`). Expression-side
   (`toSlots`/`parseNextTerm`/`concatSlots`/`replaceMediaLiteralsAndInvalidOps`)
   needs the equivalent rewrite against `binary_operator`/`comparison_operator`/
   `unary_operator`/`call`/`attribute`/`subscript`/`slice`/`lambda`/
   comprehension nodes. Recommend porting one statement type at a time with
   its existing e2e tests as the acceptance check (§4) rather than a
   big-bang rewrite.
5. **Error-path rework**: replace the `CopyFailure` construction currently
   built from Skulpt's raw exception message (`e.$msg.$mangled` etc., see
   §5 for why this must change) with a message derived from `ERROR`/
   `MISSING` node positions.
6. **Delete now-dead code**: `checkValidMatchContent` (pending confirmation
   in step 4), `debugToString` (or reimplement trivially against
   tree-sitter's own `node.toString()`), the `Sk.ParseTables.number2symbol`
   dependency.
7. **Add Vitest** (new devDependency + minimal config) and write unit tests
   directly against the new parsing module for the construct matrix in §4,
   independent of the e2e suite — faster feedback loop for the rewrite
   itself and permanent regression coverage that doesn't need a browser.
8. **Run full existing e2e suite**, fix fallout (expected: the
   Skulpt-message-dependent error-text assertions, see §5).
9. **Manual smoke test** via `npm run serve:python`: paste a variety of real
   Python snippets (not just fixtures) into the editor, load a few
   `.spy` files from `public/book_projects`/`public/demos`, confirm visually.

## 4. Test strategy

### 4.1 Existing regression tests usable as the safety net

A subagent inventoried every paste/load-related Cypress and Playwright spec
in detail. Summary (full construct lists were captured during planning and
should guide the step-4 checklist above):

- `tests/cypress/e2e/paste-python.cy.ts`, `paste-python-mixed.cy.ts`,
  `paste-python-misc.cy.ts` — the primary paste-text-to-frames suite: full
  operator matrix, unary ops, `**` chains, star-expand, slices (all
  start/stop/step combos), ternary, comprehensions (list/set/dict/
  generator), augmented assignment (all 12 ops + bracket-insertion logic),
  `raise`, multi-target assignment, `global`, `import`/`from...import`,
  nested `if/elif/else`, nested `while`, `try/except(+as)/else/finally`
  (many combos), standalone-paste of `elif/else/except/finally` onto
  existing structure, `class` (plain/docstring/fields+methods/single+multi
  parent), `def` (incl. nested-def-forbidden-in-function), comment
  placement/reindent, blank lines, `match`/`case` (literal/OR/guard/class/
  sequence/mapping patterns, comments between cases, nested `while` inside
  a case), mixed-paste section-splitting (imports/defs/main) at various
  cursor positions, and a large set of invalid-Python error-path assertions
  with exact line numbers.
- `tests/playwright/e2e/paste-augmented-assignment.spec.ts`,
  `paste-joint-frames.spec.ts`, `structured-expressions-copy-paste.spec.ts`
  — augmented-assignment edge cases, illegal-position joint-frame paste
  rejection, and expression-fragment paste-over-selection (exercises the
  expression parsing sub-path specifically).
- `tests/cypress/e2e/load-save.cy.ts`, `load-save-share.cy.ts`, and
  `tests/playwright/e2e/load-save-*.spec.ts` — SPY header/section parsing,
  project doc (triple-quoted, multi-line, embedded quotes/`#`),
  `Disabled:`/`Library:`/`FrameState:` directives (including nested/disabled
  joint-chains), layout metadata, f-strings/media-literal fixtures, slice
  syntax, class hierarchies, share-link (`spy:` base64+deflate) loading, and
  full-corpus round-trip of every `.spy` under `public/book_projects/**`
  and `public/demos/**` (load then save, byte-for-byte).
- `load-save-frame-content.spec.ts` — generative: builds frame trees
  programmatically (not from pasted text) covering most frame types with
  fuzzed slot content, saves to `.spy`, reloads, and diffs — this
  specifically stresses the *load* (parse) path over a huge combinatorial
  surface and is probably the single best regression net for the rewrite.

Nearly all of these assert on **outcomes** (resulting frame content,
generated text, or a user-facing banner message) rather than Skulpt
internals, so the large majority should pass unchanged against a
tree-sitter-backed parser — see §5 for the specific exception.

### 4.2 Coverage gaps to fill with new tests

Constructs in `pythonToFrames.ts`'s switch statement with **no current
paste/load test coverage** (found by the same inventory pass) — decide for
each whether it's in-scope-but-untested (add a test) or genuinely
unsupported (add an explicit "rejected gracefully" test instead):

- `with ... as ...:` pasted/loaded as raw text (today only reachable by
  building the frame via the UI directly).
- Positional-only (`/`) / keyword-only (`*`) parameter markers in `def`.
- Hand-written f-string with nested expressions/format-specs through the
  paste path specifically (only load/save of pre-existing fixtures is
  covered).
- Nested comprehensions (comprehension-of-comprehension).
- Chained assignment (`a = b = c`, as opposed to tuple `a, b = c, d` which
  *is* covered).
- `async for` / `await` — currently explicitly unsupported ("pass through
  but not semantically supported"); decide if tree-sitter's parse should
  reject these outright now, or keep the current lenient behaviour.
- Walrus operator (`:=`) — not referenced by any test at all.
- `**extra` catch-all / star-patterns in `match`/`case` — explicitly noted
  as unsupported/redacted in the existing `match-statement` spec.
- Comment-block reindentation across differently-indented paste boundaries
  beyond the two cases currently tested (same-indent, and
  comment-matches-following-def).
- Bare/standalone `try` pasted as raw text (only full `try/except/finally`
  combos are pasted; solo `try` is only reached via UI shortcut + save).
- Malformed/out-of-order SPY directive lines (error-recovery for corrupt
  `.spy` metadata) — no fixture exists for this at all.
- `class Foo(Base, metaclass=Meta):` — keyword-argument class bases, beyond
  simple comma-joined parent lists.

Additionally, one item is **not** "decide whether to test" but definitely
needs a new test: decorators (`@foo` before `def`/`class`) are confirmed
unsupported (§1) — add a test asserting paste/load of a decorated
`def`/`class` produces a clear "unsupported" error rather than crashing or
silently dropping the `@...` line.

Recommend adding these primarily as **Vitest unit tests** against the new
module (fast, precise, easy to enumerate many small cases) plus a handful
of e2e tests for anything that's specifically about the paste/load UI flow
rather than pure parsing (e.g. the malformed-SPY-directive error banner).

## 5. Risks / decisions needed before or during implementation

- **Error message text will change and some existing test assertions
  encode Skulpt's exact wording.** Confirmed concretely:
  `pythonToFrames.ts`'s catch blocks build `CopyFailure` from
  `(e as any).$offset?.v?.[2]?.$mangled ?? (e as any).$msg?.$mangled` — i.e.
  Skulpt's own internal error string, not a Strype-authored one (only the
  outer wrapper "Invalid Python code imported: {errorMsg}" is
  Strype/i18n-owned). At least these existing tests assert on that raw
  Skulpt wording and will need updating regardless of how carefully the
  rewrite is done: `tests/cypress/e2e/paste-python.cy.ts` lines ~122, ~129,
  ~155 (`/invalid.*import.*line: 1/si`,
  `/invalid.*import.*operator.*line: 24/si`, includes the word "operator"
  which is Skulpt's phrasing, not Strype's).

  Tree-sitter's error reporting is structural, not diagnostic: on invalid
  input it still returns a complete tree, just with `ERROR` nodes (a span
  of source it couldn't make sense of) and `MISSING` nodes (a token it
  expected but didn't find, e.g. a missing `:`). That gives *where* — exact
  start/end row and column — but not *why* in human terms the way Skulpt's
  exception message does. So we must decide what to generate instead — a
  generic "Invalid Python code at line N" (simplest, most robust, but less
  specific for users), or an attempt to synthesise a reason from the
  `ERROR`/`MISSING` node's grammar context (possible — e.g. a `MISSING ":"`
  node at least names the missing token — but fiddly and low value beyond
  that). **Recommend the generic message** and updating the handful of
  affected tests to match — flag this as a user-facing wording change
  worth a quick sanity check with whoever owns Strype's UX copy.
- **`.wasm` sourcing (build vs. vendor prebuilt)** — see §1, needs a
  decision before step 2 of the implementation plan; affects CI tooling
  requirements (Emscripten) if we build ourselves.
- **Scope of newly-supported constructs** — positional-only params, chained
  assignment, walrus, etc. (decorators are settled — see §1, confirmed
  unsupported) are grammatically parseable by tree-sitter but currently
  absent from Strype's paste support. Confirm with product/UX whether any
  should be newly supported as part of this work, or all deliberately still
  rejected (with a clear error) to keep
  this a parser swap rather than a feature expansion.
- **`checkValidMatchContent` removal** — plausible per §1 analysis but must
  be verified empirically against the real grammar during step 4/6, not
  assumed.
- **Comment/extras walking API** — the single biggest unresolved technical
  unknown, called out as the first spike step (§3 step 1) specifically so
  it's resolved before the comments/blanks design (§2) is locked in.
- **Performance**: not expected to be a concern (paste/load is not a
  hot/interactive path unlike a live editor's keystroke-by-keystroke
  reparse, which is tree-sitter's actual home turf), but worth a rough
  sanity check on the largest fixtures (`public/book_projects/**`) during
  step 9.

## 6. Suggested rollout

No feature flag recommended — this is an internal implementation swap with
no user-visible change to what's supported (modulo the error-message
wording decision above), and the existing e2e suite plus new unit tests
should give adequate confidence for a direct cutover on this branch,
reviewed as a normal PR. If the team wants extra safety, a temporary
shadow-parse mode (run both parsers, log/assert equivalence on frame output
in dev builds only) could be added for a short soak period, but this adds
real complexity for what's likely marginal benefit given the test coverage
above — only worth it if the initial e2e run in step 8 turns up a
worryingly large or unpredictable diff.
